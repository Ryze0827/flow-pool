# FlowPool · GPT 账号动态调控

基于 **Python / FastAPI + Vue 3 / Vite + SQLite** 的单机管理系统。账号管理、调度写入和用户倍率纠正通过 Sub2API 管理员 API 完成；配置 PG 后，调用统计、调度采样与倍率巡检通过 PostgreSQL 只读查询聚合；未配置时使用管理员 API，不直接修改上游数据库。账密登录可选本地官方认证或 Session Studio 第三方通道，后台解析凭据并生成待确认批次后，再通过管理员 API 入池。

## 一键运行

需要 Python 3.10+、Node.js 18+（推荐 22 LTS）。首次启动会创建 `.venv`、安装依赖并构建前端；已安装 nvm 的机器会自动尝试 Node 22 / 20。

```bash
./start.sh      # 安装依赖、构建、后台启动
./stop.sh       # 停止
./restart.sh    # 重新构建并重启
./status.sh     # 查看状态
```

访问 **http://127.0.0.1:8765**。可用 `PORT=8877 ./start.sh` 更改端口。脚本支持从任意工作目录执行，也支持包含空格或中文的工程路径。

运行日志：`data/service.log`。前端由 Python 服务直接提供，正常运行只需要一个后台进程。进程通过文件锁保证一个数据库只有一个调度 worker；不要配置多个 Uvicorn worker。

首次部署前，在工程目录创建仅本机可读的 `.env`（不要提交到 Git）：

```bash
cat > .env <<'EOF'
FLOWPOOL_SUB2API_URL=https://mgr.aiwxin.com
EOF
chmod 600 .env
```

管理员使用与 erxinai 一致的 **Sub2API 邮箱和密码**登录，支持 Turnstile 和 TOTP 二步验证，仅允许 `role=admin` 且 `status=active` 的账号，不提供注册入口或注册代理。登录协议迁自 erxinai 的 `src/api/auth.js`、`src/auth/LoginPage.jsx` 和 `TurnstileWidget.jsx`；令牌保存在服务端加密存储中，浏览器只持有 HttpOnly 会话 Cookie。会话最长 12 小时，期间按需刷新上游令牌，每次访问受保护 API 都向 `/auth/me` 核验管理员身份。禁用、降权、令牌吊销后不能继续访问；上游暂不可用时拒绝操作但保留会话供稍后重试。

`FLOWPOOL_SUB2API_URL` 是登录和管理操作的统一后端地址，示例与 erxinai 当前 `.env.local` 一致。部署同机时可改成该后端实际监听的回环地址；**不要填 erxinai 前端地址或另一套 Sub2API**。环境变量优先于本地已保存的连接地址；未设置时可沿用已保存的地址。页面不允许单独切换登录/管理后端。旧版 `FLOWPOOL_ADMIN_*` 不再生效，旧本地登录会话不再接受，无需迁移用户或密码。切换上游实例前应先处理本地托管账号及导入记录，避免混用 ID。

默认允许通过 `fp.aiwxin.com` 访问；使用其他 Nginx 域名时，将域名加入 `FLOWPOOL_ALLOWED_HOSTS`，正确传递 Host、`X-Forwarded-Proto`，对外使用 HTTPS。Uvicorn 只应信任实际反向代理的 IP（默认信任回环地址），应用按经可信代理处理后的请求协议设置 Secure Cookie，不直接信任任意客户端的转发头。启用 Turnstile 时需在同一站点配置中允许 FlowPool 域名。登录后在「连接设置 → Sub2API PostgreSQL」填写数据库主机、端口、库名、用户名、密码和 SSL 模式，并测试、保存。PG 配置加密保存在本地 SQLite，密码不回显；同一连接留空密码表示保留，也可明确勾选清除密码。改换连接目标或用户名时需重新填写密码。支持连接超时（1–30 秒）和查询超时（1–300 秒）。测试使用当前表单但不保存，核对主库、查询字段权限及与 HTTP 后端的管理员 Key 一致性。先保存上方管理员 Key，再测试 PG。

旧的 `FLOWPOOL_SUB2API_PG_DSN` 仍可作为尚未在页面保存时的配置来源（密码特殊字符需 URL 编码）；**页面保存后优先使用本地配置**，无需重启，不再受该环境变量覆盖。未保存时继续使用原 DSN 的全部 libpq 参数；页面配置使用展示的连接字段，证书验证依赖服务器上的 libpq 证书配置。共用只读连接模块位于 `backend/postgres.py`，指标查询集中在 `backend/analytics.py`。清空页面数据库用户名并保存，会停用 PG、清除保存的密码，覆盖旧环境变量并恢复 API 查询。已配置 PG 但连接失败、超时、指向副本或后端 Key 不匹配时直接报错，不静默回退、不将故障视为零数据。跨主机连接建议使用 `verify-full` 和受信任证书；本机可使用 Unix socket 或回环地址。

### 指标读取范围

| 功能 | 配置 PG | 未配置 PG |
| --- | --- | --- |
| 调用记录与总条数 | SQL 白名单字段查询、COUNT、分页 | 原调用记录 API |
| 三类号池最近调用 | 按本地托管账号在数据库筛选，每池取最新记录，不再受全站 2,000 条扫描上限影响 | 原分页扫描方式 |
| 最近 100 次调用占比 | SQL 先取全站最新 100 条，再按账号聚合，包含未托管账号的分母 | 原 API 最新 100 条 |
| 首字延迟调度样本 | SQL 按账号、数据库时间、恢复时间和记录水位筛选后 LIMIT | 原 API 采样规则 |
| 总览实时 RPM | Sub2API `dashboard/snapshot-v2` 的 `stats.rpm` | 同左 |
| 恢复调度水位 | SQL MAX(id) | 原最新记录 API |
| 用户倍率巡检及复核 | SQL 全量充值汇总与分组权限判断 | 分页用户及服务端充值汇总 API |
| 本地池数量、冷却/观察/告警统计、日志、导入批次 | 本地 SQLite/已有页面计算 | 同左 |
| 账号实时状态、导入检查、代理/分组配置、账号修改 | Sub2API API | 同左 |

数据库查询均使用绑定参数、强制只读事务和超时，只选择展示/判断需要的字段；账号、分组和倍率修改始终使用 Sub2API 接口。SQL 调用记录按完成时间、ID 倒序；调度样本排除未来/超过 5 分钟的记录、空/负首字耗时、水位之前和恢复前已在途的请求。SQL 号池结果的 `has_more` 由多取 1 条确认，`total` 仍表示本次展示条数。

## 使用流程

### 自助发票

管理端新增「发票管理」：配置金额档位与固定手续费（USD），开启自助发票后接收 erxinai 用户申请。首档金额起点必须为 0，每档适用至下一档起点；按合并后的充值入账总金额（USD）匹配最高已达到起点的档位，每次申请只收取该档固定金额，不按百分比或订单笔数计算。起点和手续费最多两位小数。例如起点 100、手续费 5，申请金额 100 或 150 USD 均收取 5 USD（未达到下一档时）。首版支持企业抬头、税号、接收邮箱和最多 100 笔整单合并，不支持部分开票和实时支付。

升级时旧百分比规则的数值转换为固定金额草稿（四舍五入保留两位小数），并关闭自助发票；管理员需核对各档金额、保存并重新开启。已有申请仍按提交时记录的手续费金额审核扣费，不因规则升级重新计算。新报价返回 `fee`（固定手续费金额）和 `fee_mode: fixed`，用户端应直接展示 `fee`。

用户端提交前显示后端报价与余额，并刷新账户余额；FlowPool 接收申请时重新验证订单、报价和余额。管理员审核通过时复核订单和余额，再通过 Sub2API `POST /api/v1/admin/users/:id/balance` 的 `subtract` 原子扣费；驳回不扣费并释放关联订单。已退款、正在申请退款及已占用订单不可重复申请。报价有效期 15 分钟，规则或订单改变后需刷新报价。

扣费成功后上传 PDF（最多 5 MB），系统保存到私有 `data/invoices/` 目录并将附件邮件加入队列。发票邮件复用「邮件通知」中的 SMTP 连接与发件配置，发送到申请填写的邮箱，不受告警通知开关或管理员收件人列表影响。邮件发送失败后在申请详情手动重发；「已提交 SMTP」不代表对方已经收到。扣费结果未确认时停止自动重试，管理员先按申请编号核对 Sub2API 余额流水，再在详情中确认已扣费或未扣费。

开票开关统一由 FlowPool「发票管理」控制。erxinai 通过带用户鉴权的 `/api/invoice-user/settings` 读取 `enabled`，不依赖 Sub2API 的支付开关；关闭后 FlowPool 也拒绝新的报价和申请，已有申请记录仍可查看。

erxinai 的 `VITE_FLOWPOOL_BASE_URL` 配置当前工程的访问基础 URL（不含 `/api/invoice-user`，修改后重新启动开发服务或构建）。本地配置为 `http://127.0.0.1:8765`，当前生产配置为 `https://fp.aiwxin.com`。Cloudflare 上修改该配置后需重新构建 erxinai。

FlowPool 默认允许 `https://aiwxin.com` 跨域访问发票用户接口，并允许 Host `fp.aiwxin.com`，后台任务默认开启；这些默认值随一键升级生效，无需手动新增 `FLOWPOOL_INVOICE_ALLOWED_ORIGINS`、`FLOWPOOL_ALLOWED_HOSTS` 或 `FLOWPOOL_BACKGROUND_TASKS`。已有环境变量仍优先，升级不会覆盖 `.env`；若已设置其他域名或 `FLOWPOOL_BACKGROUND_TASKS=0`，需调整或删除原配置。

自定义 erxinai 来源通过 `FLOWPOOL_INVOICE_ALLOWED_ORIGINS` 设置（协议、域名和端口，多个来源用逗号分隔，显式留空可禁用跨域），只对发票用户接口开放跨域，不使用管理员 Cookie；自定义 FlowPool 域名通过 `FLOWPOOL_ALLOWED_HOSTS` 设置。

若 `VITE_FLOWPOOL_BASE_URL` 留空，则沿用同源代理：开发环境使用 `VITE_DEV_INVOICE_PROXY_TARGET`（默认 `http://127.0.0.1:8765`），生产使用下方 Nginx 配置。其余 `/api/v1/*` 始终访问原 Sub2API。

本地调试可继续连接环境上的 Sub2API：FlowPool `.env` 的 `FLOWPOOL_SUB2API_URL` 和 erxinai `.env.local` 的 `VITE_DEV_API_PROXY_TARGET` 使用相同环境地址；FlowPool 前端的 `FLOWPOOL_DEV_API_TARGET` 使用 `http://127.0.0.1:8765`。设置 `FLOWPOOL_BACKGROUND_TASKS=0` 可暂停本地实例的自动调度、邮件发送及性能采样任务，页面接口仍可使用；正常运行时删除此项或设置为 `1`，上传发票后邮件才会自动发送。

使用同源代理的生产环境在 **erxinai 所在站点**增加以下配置，端口按实际配置替换：

```nginx
location ^~ /api/invoice-user/ {
    proxy_pass http://127.0.0.1:8765;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 120s;
}
```

将 erxinai 的域名加入 FlowPool 的 `FLOWPOOL_ALLOWED_HOSTS`，并确保两端使用同一个 Sub2API 后端。用户接口通过用户 Bearer Token 校验身份，管理接口仍仅接受管理员会话。备份时一起保留 `scheduler.db`、`secret.key` 和 `invoices/`；远端已发生的扣费不随本地数据库回退，恢复旧备份后应先核对待审核申请的扣费流水。

### 总览性能指标与 RPM 告警

总览「性能指标」直接读取 Sub2API `GET /api/v1/admin/dashboard/snapshot-v2` 的 `stats.rpm`，与其前端口径一致：**全站最近 5 分钟已落库调用数除以 5，取整数**，不限定 GPT 账号。后台每 30 秒独立采样，单轮最多 25 秒；关闭页面或停用账号调度后仍继续监控。前端自动或手动刷新均读取后台缓存。

RPM 无论是否配置 PG 均使用该接口，不再查 SQL 或分页调用记录。请求 `include_stats=true`，`include_trend/include_model_stats/include_group_stats/include_users_trend=false`，保留 `granularity=hour` 和 `timezone=Asia/Shanghai`。日期范围和粒度不参与 `stats.rpm` 计算，因此不发送固定日期。此接口不能单独选择 RPM 字段，会返回 stats 对象，本工程只读取其中的 RPM。使用 `generated_at` 识别快照；重复缓存快照不重复比较或发信，缺失、异常或过期数据不作为 0。切换后端、重启、查询失败或有效快照间隔超过 65 秒后重新建立基线。

增长率 = `(当前 RPM - 上次 RPM) / 上次 RPM × 100%`，**严格超过 100%（当前值大于上次两倍）**才告警，等于 100% 不告警。上次为 0 或没有可比较数据时只建立基线，不作除零判断；连续达限的不同采样分别通知，同一采样只入队一次。告警不修改上游账号或调度状态。

在「邮件通知」配置 SMTP、收件人并开启邮件通知与「RPM 增长告警」（类型默认勾选）。RPM 告警独立于账号告警间隔，邮件包含统计范围、当前/上次 RPM、增长率和采样时间。入队失败显示在性能面板；发送成功/失败可在邮件发送记录中查看。关闭通知时取消未发送的 RPM 邮件，已开始的发送可能完成。不会补发启用前的告警，也不发送测试邮件。

### 用户倍率巡检

打开「用户倍率巡检」，留空检查全部未删除用户，也可输入邮箱（换行、空格、中英文逗号或分号分隔）。配置 PG 后不分页读取用户或逐个请求充值历史：一个 PostgreSQL 一致性快照聚合 `redeem_codes` 中 `used_by` 对应用户、`value > 0` 且 `type IN ('balance', 'admin_balance')` 的全部记录，口径与 erxinai 使用的 `balance-history.total_recharged` 相同；不使用用户余额或 `users.total_recharged`，扣款、返佣和非余额兑换不计入。未配置 PG 时通过分组/用户分页、分组专属倍率和 `balance-history.total_recharged` 完成巡检；充值历史每用户只取 1 条以获取服务端的全量汇总，最多并发 4 个用户。接口模式无法提供跨请求事务快照，纠正前仍逐批复核，写入后仍回读专属倍率。

「适用分组」支持搜索并勾选当前后端正常且未删除的 GPT / OpenAI（`platform=openai`）分组，至少 1 个、最多 200 个，所有所选分组共用下方充值档位。选择和档位一同保存，按分组 ID 绑定，改名后仍适用；停用、删除或改为非 GPT 平台的所选分组会阻止巡检/纠正，需先更新选择。旧配置未选择过分组时，默认沿用「Pro号池」与「Pro号池 (强制开启Fast)」（名称按 NFKC 归一化），在页面保存后固定为所选 ID。SQL 和 API 两种模式使用相同的分组范围。「充值档位规则」支持在当前页面新增、删除和修改门槛与倍率，保存到本地 SQLite；按已达到的最高充值门槛匹配，低于最低档跳过。初始默认档位为 ≥50 / 100 / 200 / 500 美元分别对应 0.28 / 0.26 / 0.22 / 0.18，可完全替换为自定义规则。至少保留 1 档、最多 50 档；门槛必须非负且不重复，倍率为正且最多 4 位小数（与 Sub2API 存储精度一致）。未保存的编辑需先保存或撤销才能巡检/纠正。规则和数据库配置独立存储，不会被其他页面保存调度设置覆盖；修改后旧巡检快照失效，正在巡检/纠正时拒绝修改配置。用户专属倍率优先于分组默认倍率；专属组和限制公共组的用户需具备对应 `user_allowed_groups` 权限。保留禁用用户的巡检，与 erxinai 原实现一致。

数据库必须指向 **该后端 PostgreSQL 主库**，建议使用仅有 SELECT 权限的账号，允许读取 `usage_logs`、`accounts`、`account_groups`、`users`、`groups`、`redeem_codes`、`user_allowed_groups`、`user_group_rate_multipliers`，以及 `settings` 中 `key='admin_api_key'` 的记录。应用强制只读事务，查询超时默认 30 秒、可在页面调整；先核对数据库 Key 与连接设置一致，再通过 HTTP 校验 Key，每次查询均核验主库及数据库 Key；同一轮巡检、同一连接配置复用 PG 连接和一次成功的 HTTP Key 校验，配置改变后重新校验，每次查询仍使用独立只读事务，配置错配时阻止查询和相关调度/纠正。数据库账号授权由部署管理员执行，程序不建表、不改权限、不自动迁移上游数据库。

结果包含异常、充值金额、当前/预期倍率、倍率来源和未找到邮箱。选中记录后，确认弹框列出具体变更，再提交纠正。后端保存 30 分钟、最多 20 份加密巡检快照，并在提交前及每批最多 4 位用户写入前重新检查数据；数据、连接或充值档位变化时要求重新巡检。使用 `PUT /api/v1/admin/users/:id` 的局部 `group_rates` 更新，仅提交选中的分组，保留其余倍率和 RPM 设置。写入后回读主库确认，逐条报告成功或未确认，页面自动重新巡检展示最新状态；超时、部分失败及重启后的未知结果须重新巡检再操作，不自动重放。

该接口没有比较并交换（CAS）参数，复核与提交间仍有并发窗口；避免同时在其他管理页面修改同一用户倍率。实际请求计费的缓存生效时间遵循 Sub2API 自身行为。

### 页面一键升级

左上角「一键升级」升级的是 FlowPool 本身。弹框显示当前分支、提交版本、远程跟踪分支和升级进度；点击「开始升级」后，独立后台进程完成拉取、构建和重启，关闭弹框或 Web 服务重启不会中断任务。仅在打开弹框或点击「刷新状态」时读取进度，不自动轮询；升级后可手动刷新页面。

首次部署需先将工程提交并推送到 GitHub，在部署目录 clone 对应分支并通过 `./start.sh` 启动。后续从开发目录提交、push，再在部署页面升级。当前分支须跟踪 `origin`，工作区必须干净（包括未忽略的新文件）；无首个提交、本地改动、分支分叉、运行方式不匹配或自定义 `SCHEDULER_DATA_DIR` 时会阻止升级并显示原因。私有仓库使用部署机已配置的 Git 凭据，不在页面收集 Token，不弹出交互式 Git 登录。

升级先 fetch 远程分支并锁定提交，采用与 `git pull --ff-only` 相同的快进约束；已是最新时不重启。新版本在 `data/upgrades/<任务 ID>/candidate` 中独立安装 Python / Node 依赖、构建前端，并用空白数据验证启动。准备期间原服务继续运行，页面写入操作暂时阻止；正在登录的账号需完成后再升级。

启动验证隔离 Sub2API / PG 连接配置和生产 Host 限制，检查健康、匿名登录状态及页面资源可用，同时要求未登录访问设置、升级和性能接口返回 401。若旧版升级脚本在此阶段因仍要求 200 而失败，当前服务未切换；修复提交推送后，需在部署目录手动执行一次 `git pull --ff-only origin main`，成功后执行 `./restart.sh`。一键升级启动时复制的是当前版本脚本，因此不能依靠旧脚本自行完成这次修复升级。

构建通过后短暂停机，备份数据库、加密密钥、原 Python 环境和前端产物，再切换代码与运行环境。新服务健康检查完成前不启动调度和邮件任务，避免失败回退时重复执行外部操作。部署失败会尝试恢复原提交、依赖、前端与数据并重启；构建失败不会切换当前版本。升级不执行强制拉取，不清除工作区；回退仅针对本次成功快进且没有额外改动的提交。

账号、配置、密钥和升级备份均在 Git 忽略的 `data/` 中。最新状态在 `data/upgrade.json`，逐次记录及备份在 `data/upgrades/`；Python 环境可能通过 `.venv` 链接到其中的 candidate，**不要直接删除整个 upgrades 目录**。若主机断电或升级进程被强行终止，页面会提示任务中断；若自动恢复未完成，请查看任务备份和 `data/service.log`，完成恢复后再移除 `data/upgrade-deploying` 标记。页面只展示处理阶段和安全错误摘要，不回显可能含凭据的 Git / 安装命令输出。

### 账号管理

1. 使用 Sub2API 管理员登录，打开「连接设置」，核对统一的 Sub2API 地址并填写该后端的管理员 API Key，测试连接后保存。Key 留空表示保留原值。鉴权固定使用源码支持的 `X-API-Key`；Bearer 是 JWT 鉴权，不是管理员 Key 的另一种写法。
2. 「录入已有账号」可以搜索 GPT / OpenAI 平台所有分组的账号，多选后加入本地号池。三类号池为 **高权重组、风控组、三方账号组**，一个账号只能归属于一个本地分类，其它号池已录入的账号会置灰；接口也会拒绝跨号池重复录入。
3. 开启「首字延迟守护」。在「分组风控」批量开启 **高权重组、风控组、三方账号组** 内账号，也可在账号列表单独开关，默认仅风控组；可开启「只告警，不自动冷却」，达到规则后仍记录达限、巡检和邮件告警，但继续调度。冷却前按固定顺序保障可用性：已有高权重账号调度则复用，否则优先三方、再高权重；均不可用则不允许冷却。开启风控的账号共用规则，账号和分组开关立即生效，参与自动采样、暂停、冷却和恢复观察，所有号池仍可手动暂停 / 恢复。已有账号录入仅保存本地分类，不改变上游账号分组、优先级或原有调度开关。号池名称本身不隐式修改账号权重。
4. 「快速上号」选择 JSON 文件，设置参数和 GPT 上游分组，点击「校验并预览账号」，再点击「推送入池」。成功导入会开启账号调度；所属号池已选入守护范围时进入恢复观察期。
5. 「账号调用记录」菜单从 Sub2API 读取管理员调用日志，只展示账号、模型、推理强度、分组、首字 / 总耗时和时间，并支持分页刷新。
6. 账号详情可查看当前样本、首字延迟、统计边界与记录 ID 水位；操作日志记录自动和手动决策。
7. 「调度规则」中的「达限累计后冷却」列出冷却账号、原因、每秒更新的倒计时和预计恢复时间。到期后的下一轮后台巡检自动恢复，也可点击「立即启动调度」提前结束冷却；成功恢复后移出冷却列表、清空达限计数并进入新的观察期，失败则展示原因供重试。
8. 「调度规则」页面会展示各守护分组的首字延迟巡检记录，包括账号所属号池、样本数量、超限占比和实际措施（例如「停止调度」「保持调度」）。

所有状态的账号均可直接移出本地号池，无需先恢复调度。移出只结束本地托管及待执行的暂停、冷却恢复任务，不删除上游账号、不修改上游调度开关；历史日志保留。

上游分组用于 Sub2API 实际流量路由；本地三类号池仅用于本系统分类。只有用户主动导入 / 原位更新时，才按上号参数设置上游分组。正常录入和本地分类不修改上游分组；三方账号自动冷却会通过管理员 API 临时切换为生图分组，结束后绑定全部正常状态的 GPT 分组。

## 调度语义

默认规则可在页面动态修改：

| 参数 | 默认值 |
| --- | --- |
| 守护分组 | 仅风控组，可多选高权重组 / 风控组 / 三方账号组 |
| 有效调用时间窗口 | 最近 5 分钟（固定，按调用完成时间） |
| 有效样本数量 | 5 分钟内最近 10 条 |
| 首字延迟阈值 | 严格大于 10,000 ms |
| 触发慢调用占比 | 大于等于 50% |
| 只告警，不自动冷却 | 关闭 |
| 达限滚动窗口 | 120 秒（可配置） |
| 窗口内停调次数 | 2 次（可配置） |
| 计次最小间隔 | 30 秒（可配置） |
| 再次计次新样本比例 | 配置样本量的 50%，向上取整（可配置） |
| 冷却时长 | 每次固定 1,200 秒（20 分钟，可配置） |
| 恢复观察时长 | 60 秒 |
| 检查间隔 | 每轮完成后等待 15 秒 |

- 正常阶段只从最近 5 分钟内取最新 10 条有效首字延迟记录，凑满才判断，绝不从窗口外补足样本。5/10 即记一次达限，滚动窗口内累计达到配置次数后才尝试停调；次数不足只告警，继续调度。开启「只告警，不自动冷却」后，无论累计次数是否达到阈值都只记录告警并继续调度。缺失 / 负数 `first_token_ms` 的记录不计入分母，不用总耗时代替首字延迟。
- 每个账号独立保存达限时间，按 `(当前时间 - 窗口时长, 当前时间]` 计数，不要求连续达限。首次达限计一次；再次计次必须距离上次实际计次至少 30 秒，并有至少配置样本量 50% 的新调用（向上取整，10 条需 5 条新调用，5 条需 3 条）。新调用以 ID 超过上次计次样本最大 ID 判断，等待确认的巡检不更新基线；仅旧样本过期、重排或次数滑出累计窗口不计新达限。5 分钟内没有有效调用时清空告警和累计次数。计数重启后保留，过期次数失效；恢复调度或修改达限规则（开关、采样量、阈值、窗口、次数、计次间隔、新样本比例）后重新计数。巡检记录保存当次计数和规则快照。
- 首字延迟自动守护支持账号级开关，账号列表可单独开启或关闭，所有开启账号共用调度规则。调度规则页的分组开关立即批量覆盖组内全部账号（包括单独关闭的账号），并作为新录入账号的默认值；只有所属分组已纳入守护时才能修改账号开关；未纳入时页面禁用开关，接口拒绝修改，历史账号开启状态也不参与守护。总开关关闭时不进行新的自动判断。修改账号风控时清空该账号的样本和计次，恢复时间边界仍保留。账号风控仅控制首字延迟守护，不修改上游调度开关或自动重登规则。取消守护不会遗留自动停调：已有冷却继续倒计时，到期恢复后回到正常调度，不再进入观察期；手动暂停仍需手动恢复。
- 使用 `/admin/usage` 返回的已完成调用记录，按 `created_at DESC, id DESC` 取最近有效样本。错误请求中没有首字延迟的记录不在此规则统计范围。
- 守护账号自动停调前（包括重启后的待完成停调）只确认上游「Pro号池」是否有其它可用的本地托管账号，不再要求覆盖目标账号的其它分组。按上游分组完整名称 Pro号池识别（忽略大小写和首尾空格，不匹配带后缀的其它专线）；所有守护分组统一先检查高权重组，存在正在调度的可用账号则无需新启用账号；否则优先选择三方账号组，再选择高权重组，不选择风控组，并排除目标账号自身。三方已有可用账号正在调度时直接复用，否则尝试开启调度，启用失败继续下一个候选，两组均不可用则当前账号不允许冷却。此规则替代原有替补分组开关（旧配置保留兼容，但不参与判断）。候选要求上游状态为 `active` 且未限流，本地不能处于暂停待确认、冷却或恢复待确认状态；手动暂停账号可作为一次性替补候选。条件不满足或无法确认时记录「暂缓停调」，下轮重新采样并检查窗口次数后重试；过期停调意图不会绕过窗口条件；错误状态或限流账号不会强行启用。手动暂停不受此条件限制。只有停调接口成功后记录「停止调度」，接口失败记录「停调未确认」。
- 自动停调后只复核一次本次选定的保障账号可用性，冷却期间不再检查替补。若本轮新开启了替补，会在巡检记录和操作日志明确写出替补账号编号；替补不可用或无法确认时提前结束本系统的自动冷却，恢复冷却账号，仍在守护范围内时建立新的观察期；一次性替补检查仍遵守上游状态和限流条件。巡检记录展示「继续冷却」「提前恢复调度」或「恢复未确认」及具体检查原因。
- 风控组、高权重组保持原停调冷却逻辑，暂停使用 `/admin/accounts/:id/schedulable`。三方组达到相同冷却条件后保持可调度，通过管理员更新接口仅绑定唯一且正常的 GPT「生图」分组（按完整名称匹配）。冷却结束或手动结束后，重新读取上游全部 `openai` / `active` 分组并绑定，包含期间新建的正常分组，排除停用及其它平台分组。分组缺失、重名或更新未确认时保留待处理状态并重试，不清空绑定。冷却到期后恢复同一账号，不做账号流量转发或主动探测请求。
- 仅绑定「生图」分组的账号使用同步请求，无首字指标，所有本地号池均跳过首字延迟采样和评估，并清除旧样本与告警计次。页面标注无需首字评估；冷却倒计时和恢复任务仍继续执行。仅生图限制解除后重新建立观察时间边界，避免沿用原先的慢调用。包含其它分组的账号仍按原规则评估。
- 三方账号从手动暂停恢复时，无论此前是否属于生图冷却，均先绑定所有正常 GPT 分组（包含生图），再开启调度。在 Sub2API 手动开启时，下轮状态同步也执行该分组恢复。恢复意图持久化，分组更新失败或重启后继续重试；完成前不会将本地状态标记为已恢复。
- 三方生图冷却独立持久化，调度保持开启不会被识别为外部恢复；期间不采样、不重复检查替补。原有三方停调冷却会在升级后的下一轮转为仅生图可调度，保留截止时间；已到期则直接恢复全部正常 GPT 分组。请求超时和重启后继续未完成的分组切换，实际分组及调度开关均确认后才完成恢复，并重新建立样本时间边界。手动暂停仍会关闭调度开关；若是在生图冷却期间手动暂停，之后手动恢复也会解除生图分组限制。移出本地号池会结束托管，不再自动恢复分组。
- 所有号池的已有冷却记录若实际上仅绑定「生图」分组，即使缺少生图冷却标记，也按生图冷却处理：保留原截止时间和冷却次数，不因上游可调度而提前恢复。到期或手动结束冷却时恢复全部正常 GPT 分组；不重复发送冷却通知或拉起替补。
- 恢复时先记录当前最大调用 ID，再开启调度，保存新的恢复时间边界和 60 秒观察截止时间。利用上游 HTTP Date 对齐时间，额外保留 1 秒边界；上游不提供 Date 时使用本机时间，需保持主机时间同步。
- Sub2API 的 `created_at` 是调用完成时间，因此用 `created_at - duration_ms` 估计调用开始时间，排除恢复前已在途的调用。恢复后的记录还必须超过 ID 水位；无法确定开始时间的记录不进入恢复期样本。
- 满 60 秒后，按本轮恢复后且最近 5 分钟内的最多 10 条有效记录判断，不要求凑满 10 条。例如仅有 3 条新记录、其中 2 条超限，也记一次达限；后续计次仍需满足计次间隔及按配置样本量计算的新样本数量，证据不足只告警，本轮窗口内次数达标后才再次暂停。没有新记录则继续观察，不回看历史。下一次检查会评估新完成的样本，观察时长不等于必须在第 60 秒精确执行。
- 观察通过后仍永久保留本轮统计边界，直到下次恢复建立新边界，避免旧慢调用重新进入窗口。
- 冷却时长统一为每次固定 20 分钟，不随连续冷却次数递增；页面保留单项冷却时长配置。已有冷却继续按保存的截止时间恢复，新冷却使用当前配置。
- 自动冷却、恢复观察、记录水位和待完成的暂停 / 恢复意图都持久化。重启后继续处理；停机期间无法调用远端接口，已到期冷却会在重新启动后恢复。
- 关闭自动调度仅停止新的异常判定，已有自动冷却仍按时恢复。手动暂停账号不会被普通巡检主动开启；只有进入冷却时的替补检查可能按规则启用候选。若在 Sub2API 中重新启用，本地自动解除暂停并清空旧样本和计次，守护范围内账号建立新的观察期，同时记录同步日志。状态同步不受守护总开关限制，不算首字延迟采样；不会自动恢复上游人工设置的停用或非 `active` 状态、到期自动暂停账号。
- 上游请求失败时保留状态并记录错误，下一轮重试。每个账号最多扫描 2,000 条调用记录；达到上限仍不足有效样本则本轮不做决策。
- 暂停和恢复的远端调用使用幂等开关，本地先写入待完成意图。网络超时或进程中断后继续完成，避免只修改远端而丢失本地冷却状态。

## 邮件通知

左侧「邮件通知」（`/mail`）可独立配置 SMTP 服务器、端口、用户名、密码 / 邮箱授权码、发件邮箱、发件人名称及 TLS，字段参考 Sub2API。配置保存在本系统，不修改 Sub2API 的邮件设置，也不会读取其 SMTP 密码。默认关闭自动通知。

- TLS 默认开启：465 使用 SSL/TLS，其它端口使用 STARTTLS（通常为 587），验证服务器证书；关闭后使用普通 SMTP。
- 支持最多 20 个收件人，页面可逐行或用逗号录入。密码在本机加密保存，接口不回显；同一主机、端口、用户名和 TLS 设置下留空保留，更改其中任一项时需重新填写；密码认证必须启用 TLS。
- 可分别开启告警、冷却邮件。告警覆盖「告警」「暂缓停调」「停调未确认」，同一账号默认 900 秒内只入队一次，可调整。冷却邮件只在确认自动停止调度或三方切换为「仅生图调度」后入队，每轮冷却一次；手动暂停、持续冷却巡检不会重复发送。
- 冷却恢复通知默认勾选，受邮件总开关及独立的「冷却恢复通知」开关控制。到期恢复、手动提前结束、替补不可用而提前恢复，以及确认上游已恢复调度时，每轮冷却发送一次「冷却恢复通知」。恢复接口及回读确认成功后才入队，失败保留恢复任务；不受告警限频或守护开关影响。普通手动暂停后的恢复不发送此通知，不补发历史恢复事件。
- 邮件仅保留账号（含号池）、措施、拉起账号三行；未新启用替补显示“否”，新启用则显示账号名称和 ID。冷却措施附恢复时间，在本次替补复核完成后生成；复核失败则通知提前恢复或恢复待重试。只通知开启后的新巡检事件，不补发历史记录；修改邮件设置不会清空达限计次或改变守护规则。
- 邮件后台发送，SMTP 异常不会阻塞调度。发送队列持久化，重启后继续处理待发送通知；已在发送中但结果不明的邮件标记失败，不自动重发，以免重复。关闭总开关或某类通知会取消对应尚未发送的任务，已开始发送的任务可能已提交。
- 「测试连接」只连接并验证 SMTP，不发邮件；「发送测试邮件」使用当前表单配置发送至填写的收件人，不受自动通知开关限制，二者均不会自动保存表单。
- 页面每 10 秒刷新发送记录，可查看邮件内容和失败原因，展示最近 100 条，保留约 10,000 条已处理记录。「已提交 SMTP」代表服务器接受邮件，实际送达请查看收件箱和垃圾箱。

## JSON 导入

支持以下结构：

- 单个对象：`{"email":"...","access_token":"...","refresh_token":"..."}`。
- 上述账号对象的数组。
- Sub2API 导出中的 `{"accounts":[{"platform":"openai","type":"oauth","credentials":{...}}]}`。
- Codex `auth.json` 中的 `{"tokens":{"access_token":"...","refresh_token":"...","id_token":"...","account_id":"..."}}`。
- API Key 账号：`{"credentials":{"api_key":"...","base_url":"https://..."}}`，或 Codex 的 `OPENAI_API_KEY` 字段。

单文件最多 500 条，页面限制 7 MB。示例可在「快速上号」下载。OAuth 凭据仅做结构检查，真实有效性由 Sub2API 处理；解析 JWT 只用于提取邮件 / 账号元信息，不用于身份认证。JSON 顶层 `expires_at` 作为账号有效期，`credentials.expires_at` 属于凭据数据；不混用两者。

导入可设置名称模板、并发、优先级、计费倍率、负载因子、多个 GPT 上游分组、代理、备注、到期自动暂停和混合渠道风险确认。本地号池独立选择，快速上号默认进入三方账号组，可在上号设置中修改并保存默认值。

JSON 和账密上号共用模型白名单和模型映射。设置页「同步最新支持模型」补齐内置 OpenAI 清单并保留自定义项；内置清单随 `backend/model_catalog.py` 更新。确认推送时，新建或原位更新账号后调用该账号的上游模型同步接口，将内置模型、上游实时支持模型和用户白名单合并去重，以同名映射写入 `credentials.model_mapping`；保留已有映射，显式配置的映射优先。白名单填写完整名称，不支持通配符；显式模型映射的请求名称仍支持末尾一个 `*`。上游同步失败、返回空清单、合并超过 200 项或写入回读未确认时，该行标记失败，不执行后续开启调度，可按已有账号 ID 重试，不重复创建。失败前账号可能已在上游创建或更新。重复账号选择「跳过」不执行同步。自动重登仍只更新认证字段，不改模型配置。

重复账号默认按名称 / 邮箱跳过；也可原位更新，保留账号 ID 和使用历史，不删除后重建。生成预览即固定本批参数；修改参数后需重新生成预览。已完成和已跳过条目不会重复执行；成功后清除暂存凭据。

每条创建使用稳定 `Idempotency-Key`。创建超时或进程中断时标记待核对，重试前查询同名账号，仅在唯一匹配时接续入池，不盲目重建。无法唯一确认时需先在 Sub2API 核对。部分失败可从最近导入批次继续重试。清除批次只删除本地导入记录，不删除远端账号。

## 批次推送后的 5 分钟观察

每次批次推送结束后，本次成功入池的账号统一观察 300 秒，覆盖高权重、风控和三方号池；跳过、失败和重试时已完成的账号不重新计时。成功后立即唤醒后台巡检，观察期间单轮完成后的等待时间最多 20 秒。截止时间和检查结果持久化，关闭页面不影响，服务重启后继续未到期的观察；历史批次不补建观察任务。

观察期内上游 OAuth 账号进入 `error` 状态时，使用加密保存的账密、可复用 2FA 和原登录通道自动重新登录，通过管理员 API 更新原账号认证字段并确认恢复调度。上游因 error 自动关闭调度仍可恢复；人工暂停、停用、到期、限流、过载、临时禁调及本地冷却不触发此观察重登。没有可复用账密（如纯 JSON 或一次性验证码导入）会提示人工处理。并非所有错误都可由重登解决：失败至少间隔 60 秒重试，连续第 4 次失败后停止，成功后清零。登录通道串行，等待时不阻塞其它账号巡检。

已在窗口内启动的重登允许完成，但自动恢复不会延长原 5 分钟截止时间；窗口结束后不再启动此次批次观察的重登，三方账号仍沿用原有认证巡检规则。首字延迟守护账号在这 5 分钟内暂不自动冷却；正常恢复仍建立新样本边界。关闭自动守护、移出号池、手动暂停、清除批次、改换账号所属池或账密、重新推送该账号及切换连接会阻止在途结果继续写入。批次列表展示观察倒计时、自动检查结果和重登异常，不回显账密或令牌。

## 三方账号认证巡检与自动重登

守护总开关开启时，三方账号除首字延迟判断外，每轮会读取 Sub2API 最新状态；仅生图账号同样检查认证状态，但仍不评估首字延迟。只有上游明确处于 error 且记录了 401 / 认证失效，才会对通过账密上号并已保存可复用材料的 GPT OAuth 账号自动重登。JSON 导入、历史未保存账密、停用、到期、手动暂停、状态切换中的账号不会自动登录；管理员 API 自身 401 只报连接异常，不能当成账号失效。

新账密上号成功后，在独立的 account_recovery 表中用本机 secret.key 加密保存邮箱、密码、2FA 密钥及原登录通道。预览中的材料也随批次加密，推送成功后从批次移到账号记录，接口和日志均不返回账密。沿用所选通道（默认 Session Studio），因此自动重登会将账密发送至原选定服务。六位动态验证码不能复用，不启用自动重登。JSON 原位更新会移除账号原来的账密恢复材料；移出本地号池也删除材料。历史账号请在最近导入批次中粘贴账密并成功重登一次，才可启用后续自动恢复。

自动登录在独立任务中串行执行，与手动登录共用通道锁，不阻塞其他账号巡检。失败或再次失效至少间隔 5 分钟。独立累计连续失败次数，超过 3 次（第 4 次失败）后放弃自动重登，保留账号与记录供人工处理；次数持久化，重启、等待或上游状态临时恢复均不解除放弃。成功重登清零失败次数；已放弃账号须人工成功重登后才重新启用自动恢复。手动暂停、配置变化等主动取消以及进程退出不计为失败。额外验证、密码错误等会记录原因。关闭总开关、手动暂停、移出号池、更新账密或连接配置变化会阻止在途自动重登结果继续推送；升级期间不启动新自动登录。

重登只更新原账号认证字段，再清除上游错误，不重建账号、不覆盖分组、优先级或模型映射。生图冷却保留分组和原倒计时；正常账号重新建立恢复观察边界。状态说明显示自动重登能力；账号巡检和操作日志记录开始、跳过、成功或失败，不包含密码、2FA 或令牌。

## 账号、密码、2FA 快速上号

「快速上号」提供「账密快速上号」和「JSON 文件导入」两种方式。

1. 点击「上号设置」按钮，在弹框中配置本地号池、GPT 上游分组、并发和重复账号处理；选择「本地登录」或「Session Studio」登录通道。
2. 在账号列表中粘贴多行 `邮箱----密码----2FA密钥`，每行一个账号，最多 500 个；空行忽略。未开启 2FA 时保留末尾 `----`，密钥留空。邮箱重复或格式错误会提示行号，整个列表通过校验后才开始登录。
3. 点击「批量登录并预览入池」。页面逐个提交登录并显示进度，成功账号在后台立即加密保存，合并为一个待确认批次；某行失败不会中断其它行。
4. 多空间账号若返回空间列表，可在失败行下选择空间后点击「重试失败账号」。仅重试失败行，成功账号不重新登录；修改密码等信息则重新粘贴列表开始新批次。
5. 核对成功账号和目标号池后点击「确认推送入池」。此前不会创建 / 更新上游账号或开启调度。JSON 文件导入作为另一种方式保留。

批量登录期间请保持当前菜单打开；离开页面会停止提交后续账号，已提交的一行仍可能在后台完成。已成功的账号可从「最近导入批次」找回并确认，账密会加密保存用于三方账号自动重登，页面不会回显，未完成或失败行刷新后需要重新粘贴。

「最近导入批次」默认展开最新一批，可按账号名称、邮箱或上游 ID 模糊搜索全部保留历史，每页 10 批。展开后显示导入结果、最新检查时间、号池和调度状态，支持筛选需处理账号。「检查整批」实时读取 Sub2API 管理员接口中的账号状态，识别上游已记录的 401 / 登录失效、其它错误、停用、限流、停止调度和未入本地池；不发起模型调用，因此「未见异常」不等于凭据经过实际调用验证。管理员 Key 无效或网络失败会提示整轮失败，不会误判为账号登录失效，保留上次结果及其时间。

每行提供「重新登录并推送」，「查看参数 / 重试推送」可定位到原导入预览。默认复用本地加密保存的账号、密码和 2FA，沿用保存时的登录通道，无需再次填写。优先使用当前批次尚未完成的登录记录，再使用该账号的恢复记录；浏览器仅查询记录是否可用及登录通道，不接收密码或密钥。记录缺失、不完整或只保存了六位临时验证码时，才要求补填；未开启 2FA 时保存的空密钥可正常复用。也可点击「更新登录信息」手动替换，当前输入框里匹配账号的信息可用于回填。登录期间已保存记录发生变化时，取消推送以免覆盖新凭据。确认后只处理这一条，沿用原批次上号参数，校验邮箱和原工作空间，已有 OAuth 账号按原 ID 更新并恢复调度，即使原批次选择跳过重复也会更新。新凭据写入成功后清除上游原错误状态及旧令牌缓存，以恢复 401 账号；失败时不提前清除错误。其余条目不重推；登录失败保留原记录，推送失败保存加密 OAuth 凭据以供原导入入口重试。重新推送会清除该条旧检查结果，后续可再次检查。

开始批量登录时固定本批参数及登录通道，失败重试仍使用原通道；之后修改上号设置不会改变已有批次。登录重试追加到同一待确认批次，已推送或已删除的批次拒绝追加。推送失败可从原有批次重试，无需重新登录。

实现复用了附件 `customer-recovery-source.zip` 中的 MIT 登录协议代码（位于 `backend/recovery/`，保留 LICENSE）。去掉商城接管、订单绑定和仅限 ProLite 的核验；新增通用邮箱 / 工作空间一致性检查、导入批次适配和本地页面入口。JWT 元信息用于邮箱、空间和有效期一致性检查，不是签名校验器；第三方通道返回的凭据依赖所选网站的可信性。

本地登录依赖 `curl_cffi==0.13.0` 和 **Node.js 22+**。启动脚本安装 Python 依赖；认证运行环境会查找 PATH 和本机 nvm 的 Node 22 / 24。登录直连 `auth.openai.com` / `sentinel.openai.com`，不使用 Sub2API 账号代理配置、不继承系统 HTTP 代理变量。单次最多约 210 秒，同时只允许一个登录请求，失败不会自动循环重试。

本地登录的密码和 2FA 通过请求体与子进程标准输入传递；为支持自动重登，加密保存在本地数据库，不写日志、命令参数或上游账号备注。登录成功后直接沿用 SQLite 加密保存和成功清理机制；浏览器仅收到批次摘要和入池参数，不收到 OAuth 凭据。点击登录后保留输入框原文，不设置占位示例；输入内容仅留在当前页面内存，刷新或离开快速上号页面时清除。成功行的处理副本清除账密，失败行保留用于手动重试；原文未修改时可只重试失败行，修改后应重新开始批量登录。认证挑战的 Node 子进程启用权限限制，只允许读取对应脚本，不允许创建子进程或写文件。

已通过模拟密码 → MFA → 空间选择 → PKCE 交换与 JSON 导入验证，以及错误隔离、运行环境检查；未使用真实账号完成官方登录。官方协议变化、网络、地区限制、额外邮箱 / 手机验证均可能使协议登录失败，此时页面给出错误，仍可使用 JSON 导入。

### Session Studio 通道

在「账密快速上号 → 登录通道」选择 `Session Studio · session.ameng2027.xyz`。点击登录后，邮箱、密码、2FA 会发送给该第三方网站；默认选择 Session Studio，仍可切换本地登录；失败不会自动切换通道。支持多行账号以及 Base32 / otpauth 密钥，第三方通道也支持六位动态验证码。每个账号按网站前端的等待上限最多 26 分钟；所有通道共用单账号登录锁。单次登录失败不立即重试，认证巡检按上述间隔和次数重试。

接口是固定 HTTPS 地址 `POST https://session.ameng2027.xyz/api/v1/relogin`，携带 `X-Session-Studio-Relogin`、随机客户端标识，兼容普通 JSON 和带进度行的 NDJSON。网站下载 Sub2API JSON 的步骤实际在其前端生成，没有独立下载 API。本系统直接将返回的 `credential` 转为现有 Sub2API JSON 格式，复用导入规范化、模型映射、加密预览、确认入池、重复账号处理流程，不落地明文文件，也不向浏览器返回 OAuth 凭据。固定目的地址、不跟随重定向、不透传服务错误正文，避免账密出现在本地日志中。

需要额外邮箱 / 手机验证时停止自动流程并尝试取消该网站的挑战会话，提示在网站完成并用 JSON 导入。CF 人机校验、网站鉴权 / 来源限制不会自动绕过；该网站本身仍可能遇到人机验证，不能保证解决本地登录的 CF 问题。

已读取公开前端并以空请求确认接口可达（返回邮箱参数校验错误）；模拟验证流式响应、错误隔离和导入链路。未向该网站提交真实账号，真实登录成功率仍需使用者选择通道后验证。该接口来自网站前端，未确认有对外 API 稳定性承诺。

## 数据与运行边界

- `data/scheduler.db`：本地 SQLite 数据库，WAL 模式。
- `data/secret.key`：Fernet 加密密钥；管理员配置与未完成导入凭据加密保存。数据目录权限为 700，密钥与数据库为 600。
- 备份时停止服务后一起备份数据库和 `secret.key`；丢失密钥后无法解密已有配置。不要提交 `data/` 或密钥到版本库。
- 页面不回显管理员 Key、PG/SMTP 密码、远端账号凭据和代理密码；数据库诊断、上游正文及包含输入值/字典键的验证错误均不透传。所有 API 响应（含拒绝响应）禁止缓存，写请求按流限制为 8 MB。
- Sub2API 登录/管理客户端禁用自动重定向和环境代理，避免凭据被意外转发；本机后端可使用回环 HTTP，跨公网必须使用 HTTPS。
- 新导入与旧批次重试不再自动将恢复密码/TOTP 写到上游备注，账号缓存入库及输出均使用字段白名单。**旧版本已经写入上游的明文备注不会因升级自动消失**；应由管理员核对受影响账号后，经 Sub2API 接口清理，并评估是否更换已暴露凭据。本次代码变更没有修改生产备注或备份。
- 默认仅监听本机回环地址，使用同源写请求检查和 Host 限制。仅允许同一 Sub2API 的正常管理员访问；公网部署需通过 HTTPS 反向代理。
- 切换上游地址前，需移出本地账号、清空导入批次，再填入新地址对应的 Key，防止不同服务中的账号 ID 混用。
- 操作日志保留最近 10,000 条，页面显示最近 100 条；导入历史支持全部保留批次的搜索与分页。

### 本地额度展示与前端调试

账号列表读取 Sub2API 账号已有的 `codex_5h_*`、`codex_7d_*` 和 `codex_usage_updated_at` 快照，展示剩余额度比例、重置倒计时及更新时间；剩余比例为 100 减已用比例，缺少快照时按满额展示。只有 Plus 账号展示 5 小时窗口，Pro / Team 隐藏 5 小时窗口。不请求用量探测接口。

### PG 读取性能

配置 PostgreSQL 后，普通巡检从 `accounts`、`account_groups`、`groups` 读取账号状态、分组及额度快照，不再逐账号调用带运行时补充信息的详情 API。只选择必要字段，不读取凭据或备注；错误正文仅用于服务端健康分类。替补确认、启停调度、分组切换、凭据更新及写入结果确认仍使用管理员 API。原有只读账号需额外具有 `account_groups` 的 SELECT 权限，可先通过数据库连接测试核验。

巡检内按配置复用数据库连接及 HTTP 身份校验，每次读取重新开启事务，确保恢复水位读取的是新的数据库快照；后台重登子任务不共用父任务连接。批次检查仅查询本批账号 ID，无 PG 时也仅逐个查询本批账号。自动重登的调用水位统一走 Analytics，已配置 PG 时不回退 API。

调用记录分页的总条数缓存 30 秒，记录列表实时读取；期间总数和页数可能短暂滞后，缓存随连接目标变化失效。RPM 继续复用 Sub2API 的缓存快照，避免重复聚合并保持展示口径一致。PG 故障仍明确报错，不回退大规模 API 翻页。
